# 初期実装の記録

2026-10-15。GAME_DESIGN.mdとBOARD_DESIGN_ADDENDUM.mdに基づくブラウザ版の初期実装。

## 実装した範囲

- 深緑の外装、サテン金属の上下段、シャンパン色のコイン、透明な囲い、控えめな暖色光。
- 手前を支点に約±17度振れる細いレール。立ったメダルを物理計算で奥へ転がし、終端の下向きガイドから同じ剛体を上段へ落とす。
- 可動上段、固定下段、閉じた左右壁・背面・上部カバー、手前全幅の回収口。通常の横落ち・無得点回収は設けていない。
- 手持ち100枚、単発・長押し投入、画面ドラッグ、左右キー・スペース操作。
- 30枚獲得ごとのイベント、5枚の確定投入ごとのボール追加抽選、ボール3個からのJPC、10枚の直接加算、盤面への30枚／300枚払出し。
- 120枚を別々の剛体として組み立てて搬入するタワー。盤面への設置待ち、ボール上限、払出し残数の保留。
- テーマに依存しない抽選表示、演出スキップ、音・振動・軽量描画の設定。
- IndexedDBによるゲーム状態と物理ワールドの同時保存。再開、再挑戦、保存非対応時の案内、版の異なる保存データを保持する処理。

イベントのキャラクターや世界観、技能を伴うミニゲームは決めていない。現在は設計の確率表を使う中立的な抽選で、物理抽選機の結果を偽装する方式ではない。

## 試作で調整した値・機構

### 物理の単位と刻み

寸法は直径25mmのメダルを基準とするが、エンジン内の1単位をその直径に合わせた。重力も392.4単位/s²へ換算し、質量はkg、時間は秒を使う。寸法だけを拡大して重力を据え置く調整ではない。

薄いコインの積層で起きた沈み込みを抑えるため、物理刻みを初期案の1/120秒から1/240秒へ変更し、接触の剛性・許容誤差を調整した。通常のソルバー反復は12、タワーは接触でつながる領域へ追加4反復を要求する。240Hzは描画フレームレートを意味しない。

依存バージョンはRapier 0.19.3、Three.js 0.186.1に固定。Rapier 0.21.0も試したが、今回の薄い積層の検証を踏まえ0.19.3を選定した。エンジン・刻み・寸法基準は保存データの互換性識別子にも含める。

### レール

直線部分を多数の短いコライダーで構成すると、メダルが継ぎ目に引っ掛かった。直線部分は連続した面に変更した。終端は、走行床を先に終え、上側の曲面ガイドと短い側板で下向きに導く構造。経路途中で別オブジェクトへ交換しない。

### 初期配置

旧案の150枚では、拡張された14D×18Dの盤面で押す力が前まで届きにくく、100枚投入しても獲得が生じない試行があった。初期盤面を240枚に調整し、下段をほぼ六角形の密な配置とし、手前に浅い2層の山を用意した。手持ちの100枚、各抽選確率、イベント30枚の条件は変更していない。

獲得を直接発生させる救済処理は加えていない。初期の山も通常の剛体で、押し台と接触した結果として落ちた分だけを数える。

### タワー搬入

横の扉を開く方式から、右奥の閉じた機構室内で上下するリフトに具体化した。下段の一部を兼ねる支持台を空きがある時だけ下げ、下の囲われた空間で120枚を用意し、ガイドとともに上げて受け渡す。受け渡し後にガイドを下へ退避し、支持台は床と同じ高さに残る。

これにより、側壁を開いた際の横流出と、可動上段を貫通する搬入を避けた。既存物体の削除、タワーの一体化、HPによる崩壊判定は使っていない。タワーは1層3枚×40層。交互の角度差を小さくし、受け渡し時の支持を確保した。

## 検証

`npm test`で経済ルールと実際のRapierワールドを確認する。主な対象は、ゲージの複数発火と余り、直接報酬の二重加算、ランダム系列の独立、レールの中央・左右端での通過、囲い、回収、ワールド復元、120枚の独立した積層と支えを失った後の落下、JP300枚の保存された供給量。

`npm run build`でTypeScriptの型検査と配信用のビルドを行う。GitHub Actionsにも同じ確認を設定し、成功したビルドのdistをアーティファクトとして残す。

今回のローカル実行結果は、受け入れテスト18件すべて成功、TypeScript型検査成功、配信用ビルド成功。通常の投入を10秒間進める試行でも、実際の回収口への落下と残高の整合を確認した。

この実行環境には対応するブラウザ操作機能がないため、ブラウザ上の画面、タッチ操作、IndexedDBの実際の書込み、iPhone/AndroidのFPSは未検証。スマートフォン60fpsや900枚時の性能を達成済みとは扱わない。画面構図の座標上の収まりと、物理・ルールのテストは分けて確認する。

物理ライブラリ内から初期化引数に関する非推奨警告が出る場合がある。アプリのビルド・ワールド生成を妨げるエラーではない。

## 次の調整

まず実機ブラウザで画面と操作を確認する。その後、初期100枚での継続時間、イベントの間隔、球やタワーの滞留、端末の負荷を調整する。イベントのテーマはユーザーとの相談で決める。

## 2026-10-15 公開後の調整

- 初期盤面を240枚から360枚へ増量。下段約7割・上段約3割とし、押す力を伝える密な下地の上に、同一層内の間隔を確保したランダムな表面層を重ねる。表面層ごとに位置と向きを変え、重力で安定化する。タワー搬入位置は確保する。抽選と独立した乱数系列を使う。
- 手持ち0枚で確認ダイアログを一度表示し、「はい、100枚追加」で無料補充する。盤面・ボール・払出し待ちは維持し、獲得・抽選進行とは別の補充累計に記録する。辞退後は落下待ちを続け、画面下から再度追加できる。
- Web Audioによるオリジナルの8小節・100 BPMのBGM。柔らかい鍵盤音、和音、低音を小さめの音量で重ねる。開始画面で音を選べ、サウンド全体のミュートに加えBGMのみの切替も保存する。一時停止・設定・補充確認中はBGMも停止し、非表示時はAudioContextを休止する。
- 既存セーブの盤面・音の設定は維持する。新配置は「はじめから遊ぶ」で反映。追加したBGM・補充累計のフィールドは旧セーブからの読込時に補完する。

追加テストは補充の二重加算防止・旧セーブ互換・不規則な初期配置・音声スケジューラの停止と切替を対象とする。音声テストはAPI代替による制御検証であり、実際の聴感やiPhoneでの再生・操作・性能を検証したものではない。

タワー崩壊テストで、手前へ落ちたメダルが跳ね返って床下へ進み、回収条件から外れる問題を確認した。手前の縁より下を通過したことを剛体ごとに保存し、跳ね返っても回収口へ落ちた分は一度だけ獲得するよう修正した。横・奥からの落下を獲得扱いにはしない。

密な積層では復元後の接触計算に小さな差があるため、保存テストは復元直後の座標一致に加え、30物理ステップ後の差を0.025D（0.625mm）以内で確認する。抽選結果・残高・払出し権利は一致を確認する。
